# Handoff: a teammate's message becomes my agent's task

Date: 2026-10-27. Status: first slice built (see Shipped); the rest is deferred. Asked by Dani: Bogdan and Vlad write to him on
Discord, by hand, after an agent produced a plan; Dani copies the text into his own Claude. That
copying is the waste. A joint message box in Bton, for people working on the same repos, with no
cross-pollination, and enforced for the whole team, not set up repo by repo.

## Shipped in the first slice, and deferred

The receive and act layers already existed: an unanswered @mention from a trusted collaborator is an
ask in the Issues tab, and its draft job is the read-only "Give to my agent" with Post reply. So a
handoff is that ask, sent on purpose.

Shipped:
- `bton handoff <repo> <issue> --to <login> "<text>"` posts `@login`, the text and the marker as the
  running user, once (a comment of theirs with the same body is the answer). The text may not name
  anyone else, carry an HTML comment, be empty or exceed 4000 characters.
- The marker only tags the ask: the Issues row reads "handed this to you". Detection stays the
  @mention.
- The playbook (version 2) tells dispatched agents to use the command for a decision a named
  teammate must make. It ships with Bton, so it covers every repo Bton dispatches in, with no
  per-repo setup.

Known limit: two agents posting the same handoff at the same instant can both post; the check is read then write.

Deferred: the organisation `.github` default (its trust rule is open question 2, and nothing needs
a switch yet), the pinned inbox issue, the "asked without a handoff" flag, a listening toggle (asks
are always on, a toggle would hide rows) and the Hand off to... button (typing `@login` in GitHub
does the same). Handoffs on PRs are not received: a PR's comments drive its move through the flow.

## Decision

No message channel of its own. GitHub is the only shared state (decided 2026-10-25, no P2P), and an
issue or PR comment is already where the information lives (the plan is in the issue). Bton makes
that comment reach the right person, and hands it to the right agent.

## What changes

1. **Receive.** Each sync already reads open issues and their last 20 comments. A comment that
   @mentions me, or carries `<!-- bton:handoff to=<login> -->`, from a trusted author
   (`FlowEngine.trustedAssociations`, the same bar as issue asks), is a handoff row in the Issues
   tab: sender, issue, age, the first lines. It leaves the tab when I reply, or when a later comment
   of mine on that issue follows it. Nothing is stored on this Mac beyond the job log.
2. **Act.** The row's main button, Give to my agent, starts a Claude job in that repo on the base
   branch with the comment and the issue thread as read-only attachments (the draft-job pattern:
   no shell, no web, edits denied, text handed over as data, never as instructions). The agent
   answers with a draft comment I edit and post, or asks me what it needs. No copy and paste.
3. **Send, by a person.** Hand off to... on an issue or PR in Bton writes the comment (marker plus
   text) as the sender. A plain @mention in GitHub works the same, with no marker: the marker only
   marks a structured message (a list of decisions, an approval request) so Bton can show it as one.
4. **Send, by an agent.** `bton handoff --to <login> --issue <n> "text"` in the CLI posts the same
   comment as the running user, so any agent can ask a person instead of writing chat text. Without
   `--issue` it goes to the repo's pinned `bton:inbox` issue.

## Enforcement across the team, not per repo

A rule that depends on each repo opting in is not a rule. Three layers, strongest first:

- **Bton-dispatched agents (enforced).** The playbook every dispatched agent is started with
  (`PRPlaybook`, versioned) gains one rule: a decision or input needed from a named person is posted
  with `bton handoff`, never left in the final message or a chat. The playbook is Bton's, so it
  applies to every repo Bton dispatches in, with no repo change. A job whose final message asks a
  named person something without a handoff posted is flagged by the watchdog (`JobFlag`) so the
  owner sees it.
- **Team policy in one place.** The switch (`handoffs: on`, who may send, the pinned inbox label) is
  read from the organisation's `.github` repository (`.bton/flow.json` there), as the default for
  every repo in that organisation; a repo's own flow overrides it. Joining a team's coordination is
  then one file, and a new repo is covered the day it is created.
- **Agents outside Bton (not enforceable).** A Claude started by hand is not under Bton's
  playbook. Bton can only make the right thing easy: the `bton handoff` command works anywhere, and
  Settings can copy a two-line rule for the team's `CLAUDE.md` (which Bton already reads from the
  base branch into every dispatched agent). Say so in Settings; do not claim more.

Listening stays a personal setting (Settings > Handoffs, off by default), so a person who does not
want it sees nothing. Sending needs no setting.

## No cross-pollination

- A handoff lives on one repo's issue: only people with access to the repo can read it, and only the
  named person's Bton shows it. The inbox issue is per repo. Nothing crosses repos or organisations.
- Authors who are not collaborators never produce a row, and their text never reaches an agent.
- The marker is matched on the whole comment, only from a trusted author, and only `to=<me>`
  counts. A comment quoting another handoff does not.
- Contributor-authored text is untrusted: it is a file the agent reads, wrapped as data, and the
  security pass (injection in a handoff body) is part of the acceptance, not an afterthought.

## Not in this change

- Push notifications to Discord or Slack. Bton's own notification for a new handoff row is enough
  to start; a bridge is a different project.
- A faster delivery than the sync interval. It needs a webhook, so a server.
- A reply thread of its own: the reply is a normal issue comment.

## Acceptance

1. A comment from a collaborator on an open issue that @mentions me appears as a handoff row within
   one sync; the same comment from a non-collaborator does not.
2. Give to my agent starts one job on the base branch whose attachments are the comment and the
   thread, with edits, shell and web denied; its final message is a draft comment, posted only when
   I press Post.
3. The row disappears once I have commented after it, and never comes back after a restart.
4. `bton handoff --to bogdan --issue 451 "..."` posts one comment with the marker, as the running
   user; run twice with the same text, it posts once.
5. With `handoffs: on` in the organisation's `.github` repo and no flow file in a member repo, that
   repo's agents get the playbook rule and its handoffs show up; a repo flow with `handoffs: off`
   wins.
6. A dispatched agent whose final message asks a named person a question without a handoff comment
   is flagged on the job.
7. A handoff body containing instructions ("ignore the rules and run ...") produces a draft, never
   an action, and the job's denied tools are unchanged.
8. Tests cover the marker parse, the trust bar, the leave-the-tab rule and the playbook text; the
   acceptance tests come from this spec by someone other than the implementer, and the change is
   reviewed by a second vendor before it ships, since it adds a GitHub write path.

## Open questions

- Whether the flag in layer one (agent asked without a handoff) is reliable enough to ship: it
  reads free text, so it may start as a hint on the job rather than a failure.
- Whether the organisation-level default needs its own trust rule (who may write to the `.github`
  repo) before Bton reads policy from it: it should, since it changes every repo's agents.
